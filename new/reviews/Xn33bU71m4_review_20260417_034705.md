## Summary

This paper systematically evaluates nine mid-sized open-source LLMs (CodeLlama, Llama2, DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, WizardCoder, Phi4, Gemma3) on two core reverse engineering tasks — name recovery (function and variable names) and type inference — using decompiled and assembly code from stripped binaries. The main finding is that, without fine-tuning, all models achieve very low F1 scores (~0.03), and even with LoRA-based fine-tuning, performance remains mostly well below practical usefulness (with a few exceptions for variable name recovery reaching up to 0.33).

## Strengths

- **Addresses a genuine gap in the literature.** The observation that prior reverse engineering work picks LLMs for fine-tuning without clear justification (e.g., SYMGEN uses CodeLlama-34B, RESYM uses StarCoder-3B) is accurate and timely. Providing the first systematic multi-model comparison on these tasks is a useful service to the community.

- **Broad experimental scope.** Evaluating across four architectures (x86-64/32, ARM, MIPS), four optimization levels, two decompilers (Ghidra and IDA Pro) on real firmware, and both zero-shot and fine-tuned settings provides significant breadth. The ablations on CodeWordNet, model size variants, and decompiler effects are informative.

- **Honest reporting of mostly negative results.** The paper does not cherry-pick favorable conditions; it clearly shows near-zero F1 for type inference, near-zero for assembly-based recovery, and inconsistent fine-tuning gains. This sober assessment prevents misplaced optimism.

- **Valuable practical observations.** Findings such as prompt template design causing 4× variation in fine-tuning time (Finding 7), models failing to follow output formatting without fine-tuning (Finding 8), and training data quality mattering more than model size (Findings 4–6) are practically useful for researchers.

- **Thoughtful dataset construction.** Using debug-symbol binaries for ground truth, normalizing identifiers to VAR/TYPE/FUNC placeholders, and deduplicating across both decompiled and assembly code demonstrate careful methodology.

## Weaknesses

### Major:

- **The abstract's headline F1=0.37 claim for DeepSeek-R1 is unsupported by the presented data.** The abstract states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." However, in Table 2, DeepSeek-R1's highest fine-tuned F1 is 0.17 (variable name recovery, O0). In the type inference table, all its scores are near 0.00. No table or figure in the paper contains a 0.37 score. This is not a minor rounding or presentation issue — it is the paper's single positive claim and it does not match the experimental evidence. The actual data supports the opposite narrative: even after fine-tuning, performance is mostly very low. This discrepancy undermines the paper's core credibility.

- **No comparison with any non-LLM baselines or prior specialized methods.** The paper explicitly positions itself as a benchmarking contribution ("the first systematic, large-scale evaluation"), yet does not include any task-specific ML model or decompiler-based tool (e.g., DIRTY, DEBIN, OSPREY, STATEFORMER, SYMLM, VARBERT) as a baseline. Without this, readers cannot determine whether the near-zero F1 scores reflect LLM-specific limitations or are artifacts of the evaluation setup (placeholder normalization, strict type matching, etc.). If existing specialized tools also score near-zero under these conditions, the "LLMs are not yet ready" conclusion would need to be reframed as "this particular evaluation setup is extremely hard." This is a critical gap for a benchmarking paper.

- **The auxiliary LLM used for output post-processing is unvalidated.** All reported metrics pass through an auxiliary LLM that normalizes heterogeneous model outputs into a standard format (§3.2). The paper acknowledges that models produce wildly varying formats (chain-of-thought reasoning, refusals, multiple candidate names) and that "a single parsing algorithm cannot robustly handle the degree of variation," yet no measurement of the auxiliary LLM's error rate is provided, nor is any human-validated calibration reported. Different models' outputs may be harder or easier for the auxiliary LLM to parse, creating systematic confounds in the comparison. This is not a minor detail — it fundamentally affects whether the reported F1 differences reflect genuine model capabilities or parsing artifacts.

- **Evaluation protocol for multi-target tasks is under-specified.** The paper extends name recovery to all callee function names within a function body (not just the function name itself), but does not clearly define how F1 is aggregated across multiple prediction targets per sample. Is it token-level, identifier-level, or function-instance-level? For type inference, strict exact string matching is used, but no type normalization is described for semantically equivalent types (e.g., `size_t` vs. `unsigned long`, pointer types). This makes the extremely low scores difficult to interpret — they could reflect task formulation artifacts rather than genuine model limitations.

### Minor:

- **Overgeneralized conclusions from a constrained setup.** The title asks "LLMs As Reverse Engineers? Not Yet," but the experimental scope is narrow: GNU C code, all identifiers replaced with placeholders, a single prompt template, and no prompt engineering. As the paper itself acknowledges, deliberately not optimizing prompts is a design choice; making strong general claims ("LLMs remain fundamentally limited") from this adversarial setup is overclaiming. The findings specifically show that when fine-tuned, some models reach F1=0.33 on variable name recovery — not great, but not "fundamentally limited" either.

- **Fine-tuning setup is under-detailed and very limited.** LoRA is used but key hyperparameters (rank, learning rate, batch size, number of epochs) are not reported. The 200 steps mentioned in Table 7 appears to be a timing measurement rather than necessarily the total training — this is ambiguous. No justification for the fine-tuning configuration is provided, and fine-tuning sometimes *reduces* performance (e.g., DeepSeek-V2 variable name recovery at O1 drops from 0.10 to 0.05), which receives no investigation.

- **No variance, confidence intervals, or robustness checks.** All results are single point estimates. Given random subsampling of test functions, stochastic LLM generation, and stochastic auxiliary LLM post-processing, differences like 0.03 vs. 0.05 are indistinguishable from noise. This affects all comparative "findings" (e.g., training quality matters more than model size).

- **Training data contamination is not addressed.** The dataset is drawn from GNU software, which is widely available online and likely present in LLM training corpora. The placeholder normalization should mitigate this, but the paper does not discuss this threat to validity.

- **Firmware evaluation details are sparse.** The real-world firmware experiments (Table 6) are a valuable addition, but the source, number, and type of firmware images, as well as how ground truth was obtained for stripped real-world binaries, are not described.

### Trivial:
- Finding 4 ("training data quality matters more than model size") is speculative — it is inferred from cross-model comparisons without controlling for architecture differences, and no direct analysis of training corpora is presented.

## Nice-to-Haves

- Adding 1–2 non-LLM baselines (e.g., a decompiler heuristic or SYMLM) on the same dataset would dramatically increase the value and interpretability of this benchmark, even if with partial coverage.
- Implementing a hierarchical or partial type matching metric alongside strict matching (e.g., credit for matching base types like `int` vs `char`, or matching pointer depth) would provide a more nuanced picture of type inference capability.
- Testing multiple prompt templates and reporting sensitivity in an ablation, given that the paper itself notes prompt design affects results by up to 4× in training time.
- Including even a small-scale evaluation of a commercial model (e.g., GPT-4 on 500 samples) to provide a reference point that many practitioners care about.
- More systematic error categorization (e.g., wrong semantic category, partial matches, format failures, refusals) with frequencies across models would make the findings more actionable.

## Novel Insights

The most important finding that emerges across all reviews — and which the paper underplays — is the tension between the strict placeholder-based evaluation (which strips all identifying information, creating an adversarial setup that arguably tests pure semantic inference) and the more realistic decompiler-based scenario (where some structural information survives). The paper tests the hardest version of the problem and then draws sweeping conclusions about "LLMs as reverse engineers." The CodeWordNet ablation (showing dramatic F1 drops when switching to strict string matching) actually reveals that models are generating semantically reasonable names that exact-match scoring penalizes — this is an important nuance that deserves more emphasis, as it suggests the models have *some* relevant capability that is being obscured by evaluation harshness.

## Suggestions

1. **Correct the F1=0.37 claim immediately.** Either add the supporting data (perhaps it comes from an architecture or metric variant not shown), or revise the abstract and introduction to accurately reflect the presented results.
2. **Add at least one non-LLM baseline** — even a simple decompiler-based heuristic on the same data — so readers can contextualize whether LLMs are merely weak or are being compared against an impossible bar.
3. **Validate the auxiliary LLM parser.** Run manual verification on a random subset (even 100 samples) comparing automatic vs. human-extracted answers to establish the parser's error rate.
4. **Soften the broad claims.** Replace "LLMs remain fundamentally limited" with appropriately scoped claims like "under our strict placeholder-based evaluation without fine-tuning, mid-sized open-source LLMs achieve low F1 on name and type recovery."
5. **Report fine-tuning hyperparameters** and justify the number of training steps.
