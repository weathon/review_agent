## Summary

This paper conducts a systematic empirical evaluation of nine open-source mid-sized LLMs (CodeLlama, Llama2, WizardCoder, DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, Phi4, Gemma3) on two binary reverse engineering tasks—function/variable name recovery and type inference—across four ISAs (x86-64, x86-32, ARM, MIPS), four optimization levels, and two input representations (decompiled pseudocode and assembly). The core finding is that all models perform near-zero in zero-shot settings, fine-tuning improves name recovery modestly (up to F1 ≈ 0.33 for variable names at O0) but has negligible impact on type inference or assembly-based recovery, and model training quality matters more than parameter count.

---

## Strengths

- **Broad evaluation scope is genuine**: The paper evaluates 9 LLMs across 4 architectures, 4 optimization levels, and 2 input representations, directly addressing the acknowledged gap that prior work selects models "without a clear rationale." Tables 2–6 provide real, granular data across this grid.

- **Well-motivated normalization design**: Replacing decompiler-specific symbols with VAR_n, TYPE_n, FUNC_n placeholders (§3.1) is a principled step that reduces confounds from decompiler naming conventions and is correctly applied throughout.

- **Training quality vs. model size finding is substantively supported**: The observation that DeepSeek-R1 (a fine-tuned Qwen2.5 variant) consistently underperforms Qwen2.5 on name recovery despite identical architecture and parameter count (§4.4, Finding 5), combined with Figure 2 showing near-identical performance across CodeLlama 7B/13B/34B, provides concrete support for the training-quality-over-size claim.

- **Honest reporting of negative and mixed fine-tuning effects**: Table 3 shows fine-tuning can *reduce* performance (DeepSeek-V2 variable name O1: 0.10→0.05), and Table 4 shows fine-tuning frequently yields 0.00 on type inference, strengthening credibility relative to papers that selectively report only positive results.

## Weaknesses

### Fatal

- **Abstract/Introduction headline claim is unsupported by the paper's own tables.** The Introduction (§1, para. 3) states: *"after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37."* In the x86-64 results presented in the paper body, DeepSeek-R1 fine-tuned peaks at F1 = 0.17 (Table 3, variable name recovery, O0), 0.05 (Table 2, function name), and 0.01 (Table 4, type inference). The maximum fine-tuned score across all models is 0.33, achieved by Qwen2.5/WizardCoder/Phi4 — not DeepSeek-R1. The paper notes results for other architectures are in the appendix, but the 0.37 figure is presented as a motivating headline result with no qualification about which architecture, task, or optimization level it refers to. Presenting an unattributed number this prominently, when every visible table contradicts it, is a material integrity issue regardless of whether the appendix contains corroborating data.

- **Figure 1 is quantitatively irreconcilable with Table 2.** Figure 1's caption explicitly states it reports *"F1 Score on Function Name Recovery with and without CodeWordNet in x86-64 Architecture via Decompiled Code."* The inline approximate values show CodeLlama with CodeWordNet at O0 ≈ 0.15, Llama2 ≈ 0.18, DeepSeek-V2 ≈ 0.20, Qwen3 ≈ 0.25. Table 2, which also reports x86-64 decompiled function name recovery using CodeWordNet (per §3.4), shows CodeLlama O0 = 0.04, Llama2 = 0.01, DeepSeek-V2 = 0.01, Qwen3 = 0.05. These should be the same experimental condition; they differ by 3–5×. No explanation is given. One set of numbers is either from a different experiment or is incorrect. Since both figures are used to support the paper's core empirical claims, this discrepancy undermines confidence in the reliability of the entire result set.

### Major

- **No comparison to specialized baselines.** The paper cites SYMGEN, RESYM, VARBERT, SYMLM, DEBIN, and others as directly related work on the same tasks. None appear as baselines. The central narrative—"LLMs not yet suitable"—is essentially unanchored: it is impossible to know whether LLMs are substantially worse than specialized tools, marginally worse, or competitive on a per-task basis. The paper's own conclusion ("LLMs remain fundamentally limited") cannot be operationalized without a bar to measure against.

- **Fine-tuning is severely undertrained; conclusions about fine-tuned ceilings are not supported.** Table 7 reports fine-tuning times for *200 steps*. With 160,000 training samples, 200 gradient steps processes a tiny fraction of the available data (depending on batch size, potentially <0.3% of the corpus). Drawing broad "Findings" from 200-step LoRA runs does not allow any statement about whether fine-tuned LLMs can eventually succeed or about the ceiling of fine-tuning benefit. The result that "fine-tuning generally improves name recovery" is almost certainly true even at convergence, but whether 0.33 represents a ceiling or an intermediate plateau cannot be determined from the current setup.

- **Firmware evaluation (Table 6) lacks essential detail.** The paper evaluates on "real-world firmware" but does not identify what firmware was used, what architecture was targeted, how ground truth symbol names were obtained from stripped binaries, or how many samples were evaluated. Without this information, Table 6 cannot be reproduced or interpreted. The finding that IDA Pro outperforms Ghidra (which is itself notable and actionable) is unsupported without this context.

### Minor

- **The auxiliary LLM used for response normalization is undescribed.** §3.2 describes using "an auxiliary LLM specialized in formatting" but names neither the model, its version, nor its prompt. If this parser systematically misparses certain models' outputs more than others, every F1 score in the paper may be confounded by parsing error. A brief error-rate characterization or model description is needed.

- **Type inference degradation after fine-tuning is dismissed without analysis.** Table 4 shows fine-tuning *hurts* type inference across almost every model (e.g., DeepSeek-V2: 0.01→0.00, Qwen3: 0.02→0.00, Phi4: 0.02→0.00, Gemma3: 0.02→0.00). The paper attributes this to "strict evaluation criteria" (Finding 2), which explains the original low scores but not why fine-tuning makes scores *worse*. Catastrophic forgetting or task-format interference is the more likely explanation and deserves analysis.

- **Finding 7 (4× training time from prompt templates) is based on a single observation.** The claim rests on one data point: DeepSeek-V2's unusually long training time and one confirming experiment with CodeLlama template modification (§4.5). The effect plausibly reflects sequence length differences rather than "template quality" per se, but no controlled comparison is presented.

### Trivial

- The paper presents the headline DeepSeek-R1 0.37 result in §1 without even naming the task (function name vs. variable name) or architecture. Even if this number is valid (e.g., from an appendix table), the framing is careless and misleading.

## Nice-to-Haves

- **Few-shot or chain-of-thought prompting ablation**: The paper evaluates only zero-shot inference. Given that instruction-tuned models (Phi4, Qwen3) are designed for prompted interaction, a 3–5 example few-shot comparison would clarify whether poor zero-shot performance reflects model incapacity or prompt inadequacy.
- **Fine-tuning convergence curves**: Plotting F1 against fine-tuning steps (e.g., at 200, 500, 1000, 5000 steps) would indicate whether models are near-convergent at 200 steps or whether performance continues rising.
- **Pretraining contamination analysis**: GNU software is widely present in LLM pretraining corpora. A basic analysis of whether functions appearing in the test set appear in common pretraining datasets would strengthen the validity of zero-shot baselines.
- **Systematic failure mode categorization**: Beyond Table 8's four examples, categorizing failure modes (hallucinated names, truncated outputs, format violations, near-correct names failing exact match) would clarify which problems are amenable to more fine-tuning vs. which require architectural changes.

## Novel Insights

The most actionable finding the paper surfaces—albeit without adequate analysis—is that LoRA fine-tuning on name recovery appears to harm type inference across nearly every model tested (Table 4). This pattern is consistent with task interference during fine-tuning: gradient updates that reinforce identifier-token generation may degrade the model's ability to generate type tokens from a finite closed vocabulary. This effect, if confirmed with proper ablation (e.g., training on name+type jointly vs. separately), would be a genuinely novel finding about multi-task LoRA behavior on structured prediction tasks in the binary analysis domain.
