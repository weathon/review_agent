## Summary

This paper systematically evaluates nine mid-sized open-source LLMs (12–16B parameter range) on two core reverse engineering tasks—name recovery and type inference—from stripped binaries, using both decompiled and assembly code. The authors develop an automated evaluation framework with an auxiliary LLM for output normalization and test across 4 architectures and 4 optimization levels with 40,000 functions. The main finding is that all models achieve very low F1 scores without fine-tuning (~0.03), and even after LoRA-based fine-tuning, performance remains poor (peaking around 0.33 for variable name recovery in specific settings).

## Strengths

- **Tackles a genuinely important gap**: The paper correctly identifies that model selection in reverse engineering research lacks justification, and provides the first systematic cross-model comparison on these tasks, covering 9 LLMs across multiple architectures and optimization levels—significantly broader than prior work.

- **Comprehensive experimental breadth**: 40,000 functions across 4 architectures (x86-64, x86-32, ARM, MIPS) and 4 optimization levels (O0–O3), plus real-world firmware evaluation with two decompilers (Ghidra and IDA Pro), provides a substantial empirical foundation.

- **Valuable practical findings**: Several documented observations are useful for practitioners: fine-tuning helps inconsistently and sometimes hurts (Table 2, DeepSeek-V2 variable name O1 drops from 0.10 to 0.05); model size does not guarantee improvement (Figure 2); training quality trumps architecture (DeepSeek-R1 underperforms Qwen2.5); assembly-based recovery is essentially impossible (Table 5). These are empirically grounded insights.

- **Identifies real operational challenges**: The documentation of inconsistent output formatting, chain-of-thought verbosity in DeepSeek-R1 causing truncation, and prompt-template sensitivity affecting training time (Finding 7) provides valuable practical knowledge for researchers working with LLMs on structured output tasks.

## Weaknesses

### Major:

- **Missing comparison to specialized (non-LLM) baselines makes the core conclusion unsubstantiated**: The paper's central claim—that "current LLMs remain fundamentally limited in their ability to perform reverse engineering tasks"—cannot be evaluated without knowing how specialized tools perform on the same metric. Papers cited as prior work (SYMLM, RESYM, VARBERT, DEBIN, OSPREY) all address these exact tasks but are not used as baselines. Without this context, an F1 of 0.05 could be terrible *or* could be close to state-of-the-art under the same strict evaluation. The paper provides no way to interpret whether the reported numbers represent a real gap between LLMs and specialized approaches, or are simply a consequence of an inherently hard evaluation protocol. This is the single most important weakness because the paper's main contribution is the negative finding, and that finding is uncalibrated.

- **The auxiliary LLM post-processing pipeline is unvalidated and entangled with the reported metrics**: Section 3.2 describes using an auxiliary LLM to "normalize" model outputs into a structured schema. This is a *generative* step that could introduce errors (missing correct answers, inferring answers from partial/noisy outputs, or distorting semantics). No validation is reported—no human-checked subset, no comparison to a non-LLM parser, no error rate analysis. This compromise is especially problematic because the paper's key positive finding (fine-tuning improves performance) may be partially an artifact of fine-tuned models producing better-formatted outputs that the auxiliary LLM handles more reliably (Finding 8 confirms formatting improves after fine-tuning). Without disentangling extraction fidelity from task performance, the attribution of all F1 scores is ambiguous. (Note: the paper *does* acknowledge formatting issues in Section 4.5, so I weaken this criticism slightly—the concern is not that the paper ignores the issue, but that it does not quantify the impact.)

- **The abstract's "DeepSeek-R1 reaches F1 0.37" claim is not supported by the presented tables**: Table 2 shows DeepSeek-R1's best fine-tuned variable name F1 at O0 is 0.17, and function name F1 at 0.04–0.05. The 0.37 figure does not appear in any main-text table. The authors note that other architectures are in the appendix, but the headline claim is not traceable to the evidence provided. This is an integrity-of-reporting issue for the paper's most prominent positive result.

- **Overgeneralized conclusions from a narrow evaluation scope**: The paper title ("LLMs As Reverse Engineers? Not Yet") and conclusion ("fundamentally limited") make broad statements about LLMs generally, but only tests mid-sized (12–16B) open-source models, explicitly excluding larger and closed models. The paper uses a single prompt template from prior ChatGPT work (Section 3.2) without exploring prompt variations, and does not leverage structured output capabilities (JSON mode, function calling) that many of these models support. The title and framing should be scoped to "mid-sized open-source LLMs with zero-shot/LoRA fine-tuning" rather than "LLMs" broadly.

### Minor:

- **The task formulation for "name recovery" underspecifies the role of callee function names**: Section 2 says the task includes "all function names appearing inside the function body, which considers every callee function," but does not clarify whether library/API functions (which real tools often identify from linkage information) and intra-binary functions are scored equivalently. If the metric is dominated by library function identification from pseudocode, this may conflate two distinct capabilities.

- **Fine-tuning sometimes decreases performance but this is not investigated**: Table 2 shows several cases where fine-tuning reduces F1 (e.g., DeepSeek-V2 variable name O1: 0.10 → 0.05; several type inference scores drop to 0.00 after fine-tuning). The paper observes this (Finding 1: "gains are inconsistent and not guaranteed") but provides no analysis of *why*—overfitting, distribution mismatch, and LoRA hyperparameter sensitivity are plausible explanations that go unexplored. This weakens the paper's ability to provide actionable guidance on model selection.

- **No breakdown of performance by difficulty category**: Aggregate F1 ~0.03 could mask meaningful variation—e.g., models might perform well on common library functions but near-zero on rare user-defined types. Without distributional analysis (by type category, function family, or code complexity), the "not yet" conclusion is blunt rather than informative about where improvements are most needed.

### Trivial:

- The paper excludes larger/closed models for practical (cost/size) reasons, which is reasonable for a resource-bounded study, but the framing should acknowledge this scope limitation more explicitly.

## Nice-to-Haves

- Comparison against at least one specialized baseline (e.g., VARBERT or RESYM numbers reported on a comparable dataset/metric) to calibrate whether low F1 is a model problem or a task difficulty problem
- A validation experiment for the auxiliary LLM post-processing on a small human-labeled subset to quantify extraction error rates
- Analysis of cases where fine-tuning *hurts* performance, investigating overfitting or template mismatch as causes
- Cross-architecture summary (ARM, MIPS, x86-32) in the main text even if just as a short paragraph or summary table
- Distributional analysis (CDF or histogram) of per-function F1 scores to show whether failure is uniform or concentrated

## Removed Points

- **Reproducibility concerns about undisclosed hyperparameters (LoRA rank, learning rate, epochs, batch size)**: While the fine-tuning details are sparse, these are implementation details that would be impractical to fully enumerate in a submission covering 9 models. The overall findings (fine-tuning helps inconsistently) are unlikely to change dramatically with different hyperparameter choices given the universally low performance ranges. *Removed as a nitpick about reproducibility/implementation details.*

- **Data contamination risk from GNU software being in training data**: This is speculative—the paper uses decompiled/assembly output and placeholder-normalized code, not raw source code. Whether GNU source in training data would help with stripped binary decompiled code is far from obvious, and the near-zero results actually argue against contamination having a meaningful effect. *Removed as speculative and not supported by the evidence (the poor results themselves).*

- **Strict type matching is unfair/should be relaxed**: The paper itself acknowledges this in Finding 2, and strict matching is a defensible design choice for a precision-oriented evaluation. This is a valid suggestion for future work but not a flaw in the current study. *Moved to Nice-to-Have.*

- **Placeholder consistency/leakage concerns**: The paper doesn't specify whether FUNC1 always maps to the same function across samples, which could allow memorization. However, given that fine-tuning only reaches ~0.33 even on the best case, and the models are evaluated on 40K diverse functions, systematic memorization of placeholder→name mappings seems unlikely to be a dominant factor. *Removed as speculative.*

- **Ground-truth alignment errors in Appendix A**: While the matching process is complex, the paper describes a careful methodology. Without evidence that this process actually introduces significant errors, this is speculative. *Removed as speculative.*

- **No simple baselines (always predict `int`, common variable names)**: This would be informative but the near-zero F1 on strict metrics for types makes it clear that trivial baselines would also perform poorly. *Moved to Nice-to-Have as supplementary analysis.*

## Novel Insights

The paper reveals an interesting methodological paradox: fine-tuning's primary effect may be teaching models the *output format* rather than the *task semantics*. Finding 8 (models fail to follow output formatting unless fine-tuned or post-processed) combined with the auxiliary LLM pipeline means that much of the observed fine-tuning improvement could be formatting-compatibility gains rather than genuine reverse-engineering gains. This suggests that future evaluations of LLMs on structured output tasks should explicitly disentangle instruction-following improvements from task-ability improvements—for example, by measuring how many predictions are *well-formed* vs. how many well-formed predictions are *correct*.

- Validate the auxiliary LLM extraction on 100–200 manually checked samples and report error rates; if the extraction fidelity is high (>95%), this concern is largely addressed.
