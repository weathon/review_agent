# Expected Review Outcome:

## Summary
The paper presents a systematic empirical evaluation of nine mid-sized open-source LLMs (CodeLlama, Llama2, DeepSeek variants, Qwen variants, WizardCoder, Phi4, Gemma3) on two core reverse-engineering tasks from stripped binaries: name recovery (function and variable names) and type inference. The authors build an automated pipeline that normalizes decompiled code (using placeholders like `FUNCi`, `VARi`, `TYPEi`), standardizes prompts, and uses an auxiliary LLM to post-process heterogeneous outputs into a unified format. Experiments across multiple architectures, optimization levels, and a firmware dataset show that zero-shot models perform very poorly (F1 typically < 0.06), fine-tuning yields limited and inconsistent gains, and that evaluation choices such as using CodeWordNet and training data quality matter more than model size.

## Strengths
1. **Systematic multi-model comparison with a reasonably broad setup.**  
   The paper evaluates nine contemporary open LLMs of similar size (Table 1) under a unified pipeline across four architectures (x86-64, x86-32, ARM 32-bit, MIPS 32-bit) and four optimization levels (O0–O3), with 40k functions for evaluation and 160k for fine-tuning. Tables 2–4 (x86-64) and Tables 9–12 (other architectures) make it clear that the authors attempted to control for model size and architecture, which is useful for the community that currently picks models for RE tasks somewhat arbitrarily.

2. **Clear negative empirical result that challenges optimistic narratives.**  
   Across all tables, F1 scores are strikingly low. For example, in Table 2, even after fine-tuning on x86-64, the best function name recovery F1 is only around 0.07, and Table 3 shows that variable name recovery only reaches ≈0.33 for a few models (e.g., Phi4, WizardCoder, Qwen2.5 at O0). Table 4 shows that type inference F1 is almost always below 0.06, even post fine-tuning. Table 5 shows that function name recovery on assembly is essentially 0.0 across all models and optimization levels. This strongly supports the paper’s main claim that off-the-shelf LLMs (and even lightly fine-tuned ones) are far from being practically useful reverse engineers for types and names, which is an important corrective signal for a currently hyped area.

3. **Useful analysis of evaluation design choices (CodeWordNet and model size).**  
   Figure 1 (Page 7) clearly demonstrates that using CodeWordNet for semantic similarity dramatically changes the measured F1 for function name recovery vs. strict string match; performance plunges without CodeWordNet, which underlines how heavily conclusions in this subfield depend on this choice. Similarly, Figure 2 (Page 8) compares CodeLlama 7B/13B/34B and shows that larger model size does not reliably improve function or variable name recovery, nor type inference, reinforcing Finding 6. These visualizations are concrete and directly support the claims about metric and size sensitivity.

4. **Attention to practical issues in using LLMs as evaluation subjects.**  
   Section 3 discusses the need for an auxiliary LLM for output normalization, acknowledging that different models do not follow formatting instructions. Section 4.5 further analyzes issues like chain-of-thought verbosity, training time sensitivity to prompt templates (Table 7), and failure to adhere to structured outputs. The examples in Table 8 illustrate cases where fine-tuning helps Qwen2.5 go from noisy or wrong guesses to correct function names like `__stack_chk_fail` and OpenSSL routines. These observations will be useful to practitioners trying to use LLMs in RE pipelines.

5. **Dataset construction pipeline is thoughtful and generally well-documented.**  
   Appendix A describes a two-step process: extracting ground truth names and types from unstripped binaries, then using this information to annotate stripped binaries and replace identifiers with placeholders, as illustrated in Figure 3. This design sensibly prevents leakage of original names into inputs while preserving the mapping between placeholders and true symbols for evaluation.

6. **Contribution as a benchmark / cautionary study.**  
   Even though there is no new model, the work provides a benchmark-style evaluation for LLMs in binary reverse engineering, similar in spirit to empirical studies in other domains. The negative results and the nuanced findings (e.g., Finding 4–6 about model size and training quality) can guide future work on choosing base models and setting realistic expectations.

## Weaknesses
1. **Inconsistency and confusion around headline numbers and “best” performance.**  
   The introduction claims that “after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37” (Page 1), yet nowhere in Tables 2–6 or Tables 9–12 does DeepSeek-R1 reach anything close to 0.37 on any task/architecture combination. The largest F1 values observed are around 0.33, and those are for other models (e.g., Qwen2.5, WizardCoder, Phi4) on variable name recovery (Table 3). This discrepancy suggests either a serious reporting error or missing explanation (e.g., different subset or metric) and undermines trust in the quantitative results. The authors must reconcile this inconsistency explicitly.

2. **Evaluation metrics for name recovery are under-specified mathematically, making F1 ambiguous.**  
   In Section 3.4, the authors state that for name recovery they use SYMLM’s CodeWordNet-based semantic distance, and that “based on the sub-word comparison, the inferred name could obtain partial scores.” However, they do not specify how these continuous similarity scores are converted into the discrete counts needed for precision, recall, and F1. If each predicted name gets a score \(s \in [0,1]\) based on sub-word similarity, how is this integrated into the standard F1 formula \(F_1 = \frac{2 \cdot \text{TP}}{2 \cdot \text{TP} + \text{FP} + \text{FN}}\)?  
   - Are they using soft TP counts where each match contributes \(s\) to TP and \(1-s\) to FP/FN?  
   - Is there a threshold \(\tau\) such that \(s \ge \tau\) counts as a TP, and if so, what is \(\tau\) and how was it selected?  
   - Do they aggregate subword-level similarity across multiple arguments or across multiple function calls within a function (since they consider callee names too), and if so, how is alignment handled?  
   Without a clear mathematical description or pseudocode, it is not possible to reproduce the reported F1 scores, and the interpretation of the small differences (e.g., 0.05 vs 0.06 in Table 2) is murky. This is particularly important because, as Figure 1 and Figure 5 (Appendix, for variable names) show, the use or absence of CodeWordNet dramatically changes measured performance.

3. **Use of an auxiliary LLM for output normalization introduces unquantified noise and potential bias.**  
   Section 3.2 explains that due to heterogeneous outputs, the authors use another LLM to “post process” responses and normalize them to a schema. However, there is no evaluation of this auxiliary LLM’s accuracy:  
   - It might mis-parse outputs, especially when models generate multiple candidate names or partial lists (as described in Section 4.5), which could systematically under- or over-count correct predictions.  
   - This auxiliary model is itself a learned system whose errors may differ across target models (e.g., some models produce more verbose explanations or different delimiters), potentially biasing comparisons.  
   - There is no control experiment where some subset is hand-labeled to validate that the post-processing achieves near-perfect extraction.  
   Given that the task is essentially structured extraction (e.g., mapping `FUNC1`, `VAR2`, `TYPE3` to strings), the accuracy of this step is crucial. Without quantitative validation, the reported F1 scores in Tables 2–6 could partly reflect post-processing performance rather than underlying LLM capability.

4. **Fine-tuning methodology is shallow and poorly specified, weakening conclusions about “fine-tuning helps.”**  
   While Section 3.3 mentions LoRA and Section 4.3 describes selecting 160k training functions, critical details are missing: no batch size, learning rate, LoRA rank, optimizer settings, number of epochs, or effective number of updates per sample are provided. Table 7 suggests that the authors only run 200 fine-tuning steps, which is extremely small for a 160k-function dataset and 13–16B parameter models, especially with long prompts. This raises several concerns:  
   - With such limited training, models may not be close to convergence, so comparisons between “Orig” and “Fine” in Tables 2–4 and 9–12 may reflect random jitters rather than learned improvements.  
   - Some of the contradictory results, such as DeepSeek-V2’s type inference performance dropping to 0.00 after fine-tuning in Table 4, could be artifacts of undertraining or an unstable optimization regime rather than meaningful negative evidence.  
   - Time-to-train numbers in Table 7 are not very informative without hardware specs, batch size, and token counts per step.  
   Overall, the experimental setup is too under-specified and arguably underpowered to support strong conclusions like “Finding 1: Fine-tuning generally improves name recovery, but gains are inconsistent and not guaranteed.”

5. **Lack of statistical analysis and sensitivity checks for prompt design.**  
   All reported scores are single-point estimates; there is no reporting of variance across random seeds, multiple generations, or prompt variants. This is problematic for several reasons:  
   - The F1 values are extremely low (e.g., 0.01–0.06 in Table 2), so small stochastic changes or template tweaks can change rankings. Section 4.5 itself highlights that small prompt changes can explode fine-tuning time, and Section 3.2 acknowledges that LLMs do not follow instructions reliably. Yet, prompt sensitivity on *accuracy* is not examined.  
   - The authors use only one “established reverse engineering prompt” (Section 3.2, also shown in Figure 4(a)) without ablation on simpler or model-specific prompts. Given that some models (e.g., DeepSeek-R1) were trained to produce chain-of-thought by default, a more careful prompt design (or disabling CoT where supported) could materially change results.  
   Without at least a brief sensitivity analysis on prompts or a variance estimate across multiple random seeds, the stability of the reported rankings and findings is unclear.

6. **Positioning with respect to prior LLM-based RE work is incomplete.**  
   The related work section cites Shang et al. (2024), Yang et al. (2025), LMPA, Resym, and several classical decompiler-type recovery works. However, several closely aligned recent works are missing:  
   - **ReCopilot: Reverse Engineering Copilot in Binary Analysis (Chen et al., 2025)** directly focuses on LLMs for binary analysis and reverse engineering, covering similar tasks (function naming, types) and should be discussed and contrasted in Section 2 and near the motivation for multi-model benchmarking.  
   - **SALT4Decompile: Inferring Source-level Abstract Logic Tree for LLM-Based Binary Decompilation (Wang et al., 2025)** proposes LLM-based decompilation and could offer insight into richer input representations that might improve the studied tasks; it should be discussed in Background & Motivation and potentially in Section 5 when suggesting future directions.  
   - **An Empirical Study on the Effectiveness of Large Language Models for Binary Code Understanding (Shang et al., 2025)** is a more recent empirical evaluation of LLMs on binary understanding that seems very close in spirit; the paper should contrast its methodology, tasks, and conclusions with this study to clarify what is truly new.  
   Additionally, theoretical work like **“The Reversal Curse” (Berglund et al., 2023)** on LLMs’ difficulty with bidirectional reasoning is thematically relevant to type/name inference, and could strengthen the conceptual motivation for why these tasks are inherently difficult for current LLMs. The absence of these references weakens the claim that this is “the first systematic, large-scale evaluation” and makes it harder to judge novelty.

7. **Limited interpretability of the very low F1 scores and lack of absolute baselines.**  
   While the key message is that F1 is very low, the paper does not provide any trivial baselines such as:  
   - Randomly sampling variable names or types from a vocabulary,  
   - Always predicting a generic name like `var` or type like `int`,  
   - Using existing classical tools (e.g., Debin, StateFormer, Osprey) on the same dataset for a coarse comparison, even if not identical in input format.  
   Without these, we do not know whether an F1 of 0.05 in Table 4 or 0.07 in Table 3 is meaningfully better than chance or traditional baselines. This is especially concerning because the authors use very strict equality for types, which can drive numbers near zero even for partially correct predictions; some qualitative analysis on type inference errors would also help.  

8. **Some claims about “training quality” vs. model size are not rigorously supported.**  
   Findings 4–6 argue that “training data quality is a more decisive factor than model size,” based mainly on observations like CodeLlama and Qwen3 outperforming “larger” models and the near-flat curves in Figure 2. However:  
   - The paper does not provide any evidence or citation about the specific training corpora quality for each model; these statements are speculative.  
   - The performance differences are tiny; for example, in Table 2 and Table 3, Qwen3 is only marginally better than others in some settings, and CodeLlama is not uniformly superior.  
   - The 7B vs. 13B vs. 34B CodeLlama comparison in Figure 2 uses only x86-64 and F1; without confidence intervals, we cannot tell if these differences are within noise.  
   So while the *hypothesis* that data quality matters more than size is reasonable, the paper’s empirical evidence is too weak to state it as a firm conclusion.

9. **Some experimental design choices for tasks are debatable and under-explained.**  
   - For function name recovery, the authors extend prior work by also requiring recovery of *callee* names (Page 2), but they do not clearly define how predictions are evaluated when a function calls the same callee multiple times, or how they align predicted names to multiple call sites.  
   - For type inference, Section 3.4 applies an extremely strict equality (exact match for primitive, user-defined, composite types) but reports only F1 without any relaxed or structural metrics; given how low Table 4 and Table 11 scores are, additional metrics (e.g., pointer-level correctness, base type correctness) or breakdowns would be essential to interpret how “bad” models actually are.  

10. **Clarity and organization issues, including some table/figure mislabeling and typos.**  
    There are several confusing aspects in the presentation:  
    - On Page 6, the caption “Table 3: F1 Scores on Variable Name Recovery” appears after discussion of type inference, and Table 4 is also described; the ordering is jumbled.  
    - In Table 11 (Appendix), CodeLlama’s O2 value is “0.3” which is likely a typo for “0.03”.  
    - The text uses “Decomplied/Decomposed” interchangeably with “Decompiled” (Figures 1, 3, 5 captions and Appendix titles) which is distracting in a decompilation-focused paper.  
    - Some findings (e.g., Finding 5, 6) are printed next to figures (img-4, img-5, img-6) in a visually cluttered way.  
    While not fatal, these issues make the paper feel less polished.

Overall, while the experimental effort is non-trivial and the negative result is interesting, the methodological under-specification, metric ambiguity, missing related work, and internal inconsistency on headline numbers keep this below the bar for ICLR.

3. **Shang, X., Fu, Z., Cheng, S. (2025): “An Empirical Study on the Effectiveness of Large Language Models for Binary Code Understanding”.**

   - Actionable suggestion: Cite in Section 2 (Background & Motivation) or in Section 5 as a conceptual explanation for why reverse engineering, as a form of inversion, is hard for current LLMs, and connect to the observed failures on type inference and assembly-only name recovery.

## Questions
1. **Clarify the 0.37 F1 for DeepSeek-R1 claimed in the Introduction.**  
   On Page 1, you state that DeepSeek-R1 reached F1 = 0.37 after fine-tuning, but no table or figure supports this.  
   - On what task(s), architecture(s), and optimization level(s) was this 0.37 measured?  
   - Was it computed with CodeWordNet or strict string matching, and does it correspond to an earlier experimental configuration not reflected in current tables?  
   Correcting or reconciling this discrepancy is essential for trust in the rest of the numbers.

2. **Precisely define the name-recovery scoring pipeline using CodeWordNet.**  
   Please provide a formal description (equations or pseudocode) of how you map model outputs to F1:  
   - How do you break names into subwords?  
   - How do you compute semantic similarity using CodeWordNet, and how do you aggregate across subwords and multiple names?  
   - How do you compute TP, FP, and FN from these similarities, especially when predicted names do not align 1-to-1 with ground truth names?  
   A precise definition would substantially increase the reproducibility and interpretability of your results.

3. **Validate the auxiliary LLM post-processing step.**  
   Have you measured the extraction accuracy of the auxiliary LLM on a held-out subset where the mapping from placeholders to names/types is manually annotated?  
   - If so, please report the accuracy or error rate.  
   - If not, can you design a small-scale experiment to estimate how often the post-processing step mis-parses the outputs?  
   Evidence here could significantly strengthen your claims that observed failures are due to target LLMs rather than extraction artifacts.

4. **Provide missing fine-tuning hyperparameters and discuss convergence.**  
   Please detail batch size, learning rate schedule, LoRA rank and target modules, maximum sequence length, and total number of optimization steps (beyond “200 steps” for time measurements).  
   - Did you monitor validation performance to ensure training had not merely started but actually improved before stopping?  
   - Would running, say, 10× more steps (with appropriate compute) produce substantially different F1 scores?  
   This would clarify whether your negative results on fine-tuning are due to intrinsic task difficulty or under-training.

5. **Consider including trivial baselines or classical tools for calibration.**  
   Even if full integration is difficult, could you:  
   - Report F1 for a “constant” predictor (e.g., always `int`, always `var`, or random names from a small vocabulary) under your scoring?  
   - Or run an existing type recovery tool like Debin / StateFormer on a (possibly smaller) subset of your dataset to show the gap between LLMs and specialized methods?  
   This would help put the low F1 values in Tables 2–4 and 9–11 into perspective.

6. **Prompt sensitivity analysis.**  
   Given your own observations in Section 4.5 that prompt templates significantly affect training time and model behavior, can you comment on:  
   - Whether you tried alternative, shorter, or more constrained prompts for models like DeepSeek-R1 that tend to produce chain-of-thought text?  
   - Whether model performance on name/type inference is robust to minor prompt changes?  
   Even a small-scale experiment with 1–2 alternative prompts on x86-64 could strengthen your conclusion that these tasks are fundamentally hard, rather than simply poorly prompted.

The overarching conclusion that current general-purpose mid-sized LLMs perform poorly on reverse-engineering tasks is plausible and broadly supported by the data, but there are important methodological gaps: unclear metric definitions, under-specified and likely underpowered fine-tuning, unvalidated auxiliary LLM processing, and a major inconsistency in reported F1 values.

## Presentation Rating
2: fair.  
The paper is readable and the overall structure is clear, but several key definitions are missing or informal, some tables/figures are misaligned with text (e.g., Tables 3–4), there are typos and noisy layout choices, and the headline results are not always consistent with the tables.

2: fair.  
The contribution is primarily an empirical benchmark and negative result rather than a new method, which is fine in principle, but novelty compared to very recent empirical LLM-for-RE studies is not clearly established, and the experimental methodology is not strong enough to elevate this to a must-have benchmark.
